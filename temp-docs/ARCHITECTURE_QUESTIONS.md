## 1. Расшифровка сообщения: «перейти через nanobind на Python Stable API… бампать ничего не надо будет для 3.12+ и не free-threaded»

### 1.1 Что происходит сейчас (что такое «бампать»)

Сейчас в проекте нет abi3: `pybind11_add_module` собирает модуль под конкретную версию Python, и каждый `.so` помечен тегом этой версии (`desbordante.cpython-312-x86_64-linux-gnu.so`). Колесо получает тег `cp312-cp312-<platform>` и **устанавливается только на 3.12**.

Практическое следствие: когда выходит новый CPython (например, 3.15), нужно:

1. добавить версию в матрицу `.github/workflows/wheel.yml` (она генерируется через `cibuildwheel --print-build-identifiers`; новый интерпретатор → новая строка матрицы);
2. собрать и протестировать новые колёса на Linux/macOS × x86_64/arm64;
3. выпустить новый релиз (или перевыпустить колёса) — иначе `pip install desbordante` на новом Python не найдёт совместимого колеса;
4. обновить `pyproject.toml`/классификаторы/README.

Это и есть «бампать»: без нового релиза пользователи нового Python остаются без бинарного колеса (или собирают из исходников).

### 1.2 Что будет с abi3

Колесо `desbordante-2.4.1-cp312-abi3-manylinux_2_28_x86_64.whl` содержит `desbordante.abi3.so` и по правилам тегирования считается совместимым со **всеми CPython ≥ 3.12 с GIL** на этой платформе. `pip` на Python 3.13/3.14/3.15 выберет это колесо, интерпретатор загрузит `.abi3.so` — **без пересборки и без нового релиза desbordante**.

Именно это имеет в виду коллега: «выходит новый питон, а старые версии desbordante уже на нём работают». Формально:

* гарантия — на уровне C API (Stable ABI): функции, которые использует модуль, не удаляются и не меняют сигнатуры в рамках CPython 3.x;
* имя файла `.abi3.so` — стандартный механизм поиска расширений CPython;
* метаданные колеса `Requires-Python: >=3.12` не мешают новой версии (верхней границы нет).

### 1.3 Оговорки, которые нужно озвучить сразу (иначе будут неприятные сюрпризы)

| Оговорка | Что это значит |
|---|---|
| **Только CPython ≥ 3.12** | Linked abi3 в nanobind требует 3.12+ (нужны `PyType_FromMetaclass` и vectorcall в limited API). Для 3.10/3.11 — либо split mode, либо у этих версий остаются обычные колёса |
| **Только не-free-threaded** | Free-threaded (no-GIL) интерпретаторы **не загружают** `.abi3.so`: до 3.15 stable ABI для них не существовало, с 3.15 есть отдельный `abi3t`/`.abi3t.so` (PEP 803) |
| **Только уже собранные платформы** | Одно колесо на платформу (manylinux_2_28 x86_64, macOS arm64, macOS x86_64, …). Новая платформа (например, Windows или aarch64-linux) — всё равно новая сборка |
| **Stable ABI ≠ стабильное поведение** | Гарантируется ABI/API, но не поведение: изменения в CPython, pandas, NumPy, в самом окружении могут требовать обновления зависимостей. Тестировать новую версию Python всё равно нужно (например, пререлизы через cibuildwheel) |
| **Метаданные и зависимости** | Если в `dependencies` появятся пины (например, `pandas<3`), они могут заблокировать установку на новом окружении. Сейчас у проекта обязательных runtime-зависимостей нет — это плюс |
| **abi3audit** | Колесо нельзя просто «пометить», как abi3: cibuildwheel 4.x автоматически запускает `abi3audit --strict`; любое обращение к не-limited API провалит сборку |

### 1.4 Что это НЕ значит

* Не значит, что код можно не трогать: смена биндинговой библиотеки (pybind11 → nanobind) — это ~106 файлов, 22 `py::pickle`, 115 `.cast<T>()` и т. д. (см. `REPORT.md`).
* Не значит, что pybind11 может то же самое: в выпущенном pybind11 3.1.0 поддержки limited API нет; PR #6198 не влит.
* Не значит, что free-threaded «за компанию» начнёт работать: у него отдельная история (см. §2) и отдельный тег колеса (abi3t, только Python 3.15+ и только split mode).
* Не значит, что новый Python не потребует от нас действий вообще: тесты/CI и релиз-ноуты остаются; но **блокирующей пересборки колёс для GIL-сборок больше нет**.

## 2. Free-threaded: что это, что есть сейчас, что будет при каждом выборе

### 2.1 Что это такое

Free-threaded (no-GIL) CPython — экспериментальная (3.13, 3.14) и официально поддерживаемая с 3.14 (PEP 779) сборка без глобальной блокировки интерпретатора: несколько потоков могут одновременно выполнять Python-код. Расширения должны явно заявить о совместимости: при импорте расширения без такого заявления интерпретатор включает GIL обратно и предупреждает. Сборки обозначаются тегом `t` (`cp313t`, `cp314t`, `cp315t`).

Ключевое для нас: **гарантий совместимости C API между обычными и free-threaded сборками нет**. Stable ABI (abi3) для free-threaded появился только в Python 3.15 как отдельный вариант `abi3t` (PEP 803), а не как расширение обычного abi3.

### 2.2 Что есть в проекте сейчас

* `src/python_bindings/bindings.cpp:57`: `PYBIND11_MODULE(desbordante, module, pybind11::mod_gil_not_used())` — модуль **заявляет**, что не пользуется GIL-зависимыми механизмами (pybind11 2.13+ умеет это для Python 3.13+). Это именно заявка (слот `Py_mod_gil = Py_MOD_GIL_NOT_USED`), а не доказательство потокобезопасности.
* Код при этом содержит места, которые для честной работы без GIL требуют аудита:
  * `src/python_bindings/md/object_similarity_measure.h` — хранение `nb::object`/`py::object` в C++-объектах и вызовы Python-функций сравнения из вычислителей, которые могут исполняться в `util::WorkerThreadPool`; рядом стоит комментарий `// TODO: support no-GIL builds and subinterpreter parallelism` и `constexpr bool kEnablePythonMultithreading = false;` (то есть Python-вызовы сейчас сознательно сериализуются);
  * `src/python_bindings/py_util/logging.cpp` — реестр логгеров под `std::shared_mutex`, но с `nb::object`/`py::object` внутри; sink вызывается из потоков spdlog;
  * `src/python_bindings/py_util/py_custom_metrics.*` и `py_util/py_custom_metrics.h` — пользовательские Python-callable вызываются из C++ алгоритмов;
  * `src/python_bindings/py_util/get_py_type.cpp` — ленивые статические Python-объекты (после миграции), к которым возможен конкурентный доступ.

### 2.3 Что умеет nanobind

* `nanobind_add_module(... FREE_THREADED)` + макрос `NB_FREE_THREADED` (nanobind поддерживает free-threading с 2.2.0).
* Примитивы для точечной защиты: `nb::ft_mutex`, `nb::ft_lock_guard`, `nb::ft_object_guard`, аннотации `nb::arg("x").lock()`, `nb::lock_self()`. В обычной (GIL) сборке они превращаются в no-op, поэтому код можно писать один раз.
* **Комбинации** (проверено по `cmake/nanobind-config.cmake` и документации 3.1.0):

| Режим сборки | Python | Тег колеса | Загружается на |
|---|---|---|---|
| Обычная (per-version), как сейчас | 3.10–3.15 | `cp3XX-cp3XX` | только своя версия |
| **Linked `STABLE_ABI`** | 3.12+ **GIL** | `cp312-abi3` | все GIL-сборки ≥ 3.12 |
| `FREE_THREADED` без abi3 | 3.13t+ | `cp313t-cp313t` | только своя FT-версия |
| Split mode, `STABLE_ABI` | 3.10+ GIL | `cp310-abi3` | все GIL-сборки ≥ 3.10 |
| Split mode + `FREE_THREADED` (abi3t) | **3.15t+** | `cp315-abi3.abi3t` | все FT-сборки ≥ 3.15 |

* В linked-режиме `STABLE_ABI` и `FREE_THREADED` **несовместимы**: флаг `STABLE_ABI` на free-threaded интерпретаторе просто игнорируется (stable ABI для FT в linked-режиме не существует). Единственный путь к abi3t — split mode с `BACKEND_MODULE` и Python 3.15+.
* GIL-сборка Python 3.15 предпочитает `.abi3.so`, но умеет загружать и `.abi3t.so` как fallback (PEP 803) — то есть теоретически одно abi3t-колесо может покрыть и GIL, и FT, но только для 3.15+ и только в split mode.

### 2.4 Что происходит с каждым архитектурным вопросом, если выбрать free-threaded

| Вопрос | Влияние выбора «поддерживаем free-threaded» |
|---|---|
| Q1 (минимальная версия) | FT существует только с 3.13; abi3t — с 3.15. Если FT обязателен, минимальная версия для FT-колёс — 3.13t, а для единого abi3t-колеса — 3.15t |
| Q2 (нужен ли abi3) | «abi3 + FT» возможно только как abi3t в split mode; для linked abi3 придётся выпускать FT-колёса отдельно (без abi3-выгоды) |
| Q3 (сам FT) | Либо отказ (убрать `mod_gil_not_used`), либо FT-колёса `cp313t/cp314t`, либо abi3t (3.15t, split mode) |
| Q4 (split vs linked) | abi3t доступен **только** в split mode; если FT-стратегия — abi3t, вопрос Q4 решается автоматически в пользу split mode |
| Q5 (структура модулей) | FT-сборки требуют, чтобы все расширения были FT-совместимы (одно не-FT расширение выключает free-threading глобально); при нескольких модулях это усложняет правила |
| Q6 (суб-интерпретаторы и логирование) | FT и суб-интерпретаторы — разные механизмы, но nanobind не поддерживает ни то, ни другое «из коробки» для суб-интерпретаторов; FT-сборка не спасает логирование от переделки |
| Q7 (pickle) | FT не меняет формат pickle, но `__setstate__` с `nb::object` внутри должен быть защищён блокировками |
| Q8 (публичный API) | Для пользователя FT — это отдельный набор колёс (`cp313t`), а не изменение API; в release notes нужно явно указывать поддержку/неподдержку |
| Q9 (производительность) | FT-сборка и abi3t добавляют TLS/бэкенд-оверхед; бенчмарки нужно снимать отдельно |
| Q10 (процесс/CI) | FT-колёса — дополнительные строки матрицы (`cp313t-*`, `cp315t-*`), отдельные тесты и отдельный TSAN-прогон; это возвращает часть «бампания», от которого мы уходим abi3 |

**Практический вывод:** abi3 и free-threaded тянут в разные стороны. Разумная последовательность — сначала получить abi3 для GIL-сборок (Q1–Q4), а FT решать отдельным этапом: либо честно отказаться от заявки, либо, когда 3.15t станет массовым, добавить abi3t через split mode.

### Q1. Минимальная поддерживаемая версия Python: 3.12+ или сохраняем 3.10/3.11?

**Почему архитектурный:** от этого зависит, возможен ли linked abi3 вообще, нужен ли split mode, как выглядит матрица CI, какие обещания в `requires-python`/классификаторах, и на какой версии гоняются примеры и тесты. Это не «мелкая настройка», а выбор цепочки сборки.

**Варианты:**

| Вариант | + | − |
|---|---|---|
| **A. 3.12+ (linked abi3)** | самый простой и обкатанный путь; нет runtime-зависимостей; одно колесо на платформу для 3.12–3.15+; меньше матрица CI | теряем 3.10 (EOL 2026-10-01) и 3.11; часть пользователей может остаться без колеса |
| **B. 3.10+ (split mode)** | сохраняем старые версии; одно колесо на платформу для 3.10+ | runtime-зависимость `nanobind-backend`; нет musllinux/PyPy-бэкендов; abi3t только 3.15t+; сложнее отладка (два артефакта) |
| **C. Гибрид (3.10/3.11 обычные + 3.12+ abi3)** | поддержка всех версий | две конфигурации сборки, условная логика в CMake/CI, больше колёс; выше шанс, что abi3-режим не протестируют |

**На что влияет:** `pyproject.toml` (`requires-python`, классификаторы, `wheel.py-api`), `src/python_bindings/CMakeLists.txt`, `.github/workflows/wheel.yml`, `bindings-tests.yml`, `examples-tests.yml`, README; на структуру кода почти не влияет (все специальные правки из `REPORT.md` нужны в любом варианте).

**Рекомендация:** A. Аргументы: 3.10 уже EOL; 3.11 — единственная «жертва»; проект всё равно выпускает колёса для 3.12+, а abi3 снимает основную боль релизов.

**Если спросят «почему не сохранить 3.10 через split mode?»:** split mode — новая возможность nanobind 3.0, у неё меньше боевого опыта, появляется рантайм-зависимость и теряются musllinux/PyPy; ради одной-двух старых версий это дороже, чем поддерживать их обычными колёсами (вариант C) или отказаться.

**Если выберут B или C:** в `REPORT.md` уже описаны конкретные изменения (варианты B/C в `STABLE_ABI.md`); план работ не переписывается, меняются только сборочные файлы, CI и `requires-python`.

### Q2. Stable ABI — обязательное требование релиза или достаточно миграции на nanobind?

**Почему архитектурный:** abi3 определяет:
* нужно ли получать типы CPython в рантайме в `get_py_type.cpp` (иначе `PyFunction_Type` не компилируется под limited API);
* нужен ли CMake ≥ 3.26 и компонент `Development.SABIModule`;
* сохранится ли заявка на free-threading;
* сколько колёс выпускать и как выглядит CI.

**Варианты:**

| Вариант | + | − |
|---|---|---|
| **A. abi3 обязателен** | главная выгода: новый Python без пересборки (то самое сообщение коллеги); меньше матрица CI; меньше релизной рутины | ограничения limited API; нужен аудит кода; abi3 медленнее обычной сборки; отказ от FT в linked-режиме |
| **B. abi3 не обязателен, мигрируем только ради nanobind** | можно оставить статически получаемые типы CPython, не трогать логирование из-за лимитов; CMake 3.25; можно свободно использовать FT | сохраняется «бампание» матрицы на каждый новый Python; главная мотивация перехода теряется; миграция всё равно стоит тех же ~106 файлов |
| **C. abi3 включаем позже, но код пишем abi3-ready** | сейчас проще, потом переключение флагом | «потом» обычно не наступает; тесты на abi3 нужно будет догонять |

**На что влияет:** `get_py_type.cpp` (блокер B1), `logging.cpp` (B2), `bindings.cpp` (`mod_gil_not_used`), `statistics/bind_statistics.cpp` (кастер), `pyproject.toml` (`wheel.py-api`), CMake.

**Рекомендация:** A — при условии, что владельцы подтверждают поддержку 3.12+ (Q1). Если Q1 = «3.10/3.11 обязательны», то abi3 всё равно достижим (split mode), просто дороже.

**Если спросят «а точно ли ограничения limited API нас не заденут?»:** проверено: `nb::ndarray` не используется, `nb::dynamic_attr` не используется, трамполинов нет, кастомный caster один и использует только stable-ABI-функции (`PyFloat_FromDouble`, `PyLong_FromLongLong`, `PyUnicode_FromStringAndSize`, `PyBool_FromLong`). Единственный реальный блокер — `PyFunction_Type` в `get_py_type.cpp`, заменяется на `types.FunctionType` из рантайма.

**Если выберут B:** `REPORT.md` §4.3.4 и §4.4.6 упрощаются (можно оставить `Py*_Type`), `STABLE_ABI.md` становится справочным документом на будущее; но CI-выгоды не будет.

### Q3. Free-threaded: поддерживаем, отказываемся или делаем abi3t?

**Почему архитектурный:** это отдельная ветка эволюции упаковки (свои теги `cp313t`/`cp315t`, свои тесты, свой аудит потокобезопасности) и отдельное ограничение на abi3 (см. §2).

**Варианты:**

| Вариант | + | − |
|---|---|---|
| **A. Отказаться (убрать заявку `mod_gil_not_used`), вернуться позже** | не нужно проводить аудит потокобезопасности; abi3 в linked-режиме; меньше колёс и тестов; честная заявка вместо оптимистичной | формально теряем уже декларируемую возможность; если FT-пользователи есть — они остаются без поддержки и desbordante будет выключать free-threading у них при импорте (с предупреждением) |
| **B. Поддерживать FT без abi3** (`cp313t`/`cp314t` колёса) | FT-пользователи получают колёса; можно использовать `nb::ft_mutex` и т. д. | нужно доказать потокобезопасность Python-вызовов (аудит `md`, логирования, custom metrics); отдельные колёса и тесты; abi3-выгоды у этих колёс нет — снова «бампать» на каждый FT-релиз |
| **C. abi3t (PEP 803), только split mode, Python 3.15t+** | одно FT-колесо на платформу; в перспективе и одно колесо на GIL+FT (3.15+) | доступно только с 3.15t и только вместе с split mode (runtime-зависимость, ограничения); сейчас 3.15 только вышел — аудитория FT мала |

**На что влияет:** `bindings.cpp:57`; `md/object_similarity_measure.h`; `logging.cpp`; `py_custom_metrics.*`; CMake-флаг `FREE_THREADED`; CI-матрица.

**Рекомендация:** A на время миграции. Причины: (1) заявка `mod_gil_not_used` сейчас, судя по коду, не подкреплена аудитом — её лучше снять, чем оставить неверной; (2) abi3 и FT в linked-режиме несовместимы, а приоритет — abi3; (3) FT-путь (особенно abi3t) станет практичным после 3.15t и, возможно, после перехода на split mode.

**Если спросят «а разве сейчас у нас не работает free-threaded?»:** технически модуль загрузится на `cp313t` и заявит `Py_MOD_GIL_NOT_USED`, но это лишь декларация; при этом Python-callable из алгоритмов вызываются из воркеров, есть статические Python-объекты и реестр логов. Без TSAN-прогона и ревизии этих мест гарантий нет.

**Если выберут B/C:** добавляются задачи на аудит (TSAN, `nb::ft_mutex`/`.lock()`), отдельные строки CI и решение по split mode (для C — обязательное).

### Q4. Linked STABLE_ABI или split mode?

**Почему архитектурный:** это два разных способа получить abi3, с разной ценой владения: linked — «всё в одном колесе», split — «фронтенд + общий backend-модуль».

**Варианты:**

| Вариант | + | − |
|---|---|---|
| **A. Linked `STABLE_ABI`** | нет runtime-зависимостей; одно колесо; минимум новых сущностей; официально рекомендуемый nanobind путь | floor 3.12; abi3-оверхед (nanobind не может напрямую трогать внутренности CPython); нет FT |
| **B. Split mode** | floor 3.10; меньше размер фронтенда; единый backend для нескольких расширений; единственный путь к abi3t | добавляется зависимость `nanobind-backend`; backend — отдельное колесо на каждую версию Python (его публикует upstream, но не для musllinux); нельзя `NB_STATIC`/`NB_SHARED`; сложнее диагностка импорта |

**На что влияет:** `pyproject.toml` (dependencies, `wheel.py-api`), CMake (`BACKEND_MODULE`), CI, README, а также выбор Q1.

**Рекомендация:** A, если 3.10/3.11 не обязательны. B — только если Q1 требует 3.10 или если FT/abi3t (Q3) признан приоритетом.

**Если спросят «а что мешает взять split mode на всякий случай?»:** он вводит рантайм-зависимость и ограничения (musllinux, PyPy, статический C++ runtime), а выгода (3.10) нужна только если Q1 скажет «да».

### Q5. Структура модулей: один расширение-модуль, несколько или NB_SHARED?

**Почему архитектурный:** сейчас это один модуль `desbordante` из ~44 OBJECT-библиотек. nanobind по умолчанию статически встраивает свою библиотеку в каждый модуль (`NB_STATIC`); при нескольких расширениях рекомендуется `NB_SHARED`, а для больших проектов — split mode (единый backend). От этого зависит, как раскладывать биндинги по файлам/целям и как шарить типы между модулями.

**Варианты:**

| Вариант | + | − |
|---|---|---|
| **A. Оставить один модуль + `NB_STATIC`** | ничего не меняется в структуре; все типы видны друг другу; проще всего для проекта | размер бинарника чуть больше (одна копия nanobind — не проблема при одном модуле) |
| **B. Несколько модулей + `NB_SHARED`** | меньше суммарный размер при многих расширениях; изоляция сборки | нужно поддерживать видимость типов между модулями (единый internal ABI, одинаковые компиляторы/флаги); усложняется упаковка и тесты; для `desbordante` публичный API сейчас единый — дробление ничего не даёт |
| **C. Split mode как способ «одного общего ядра»** | единый backend; маленькие фронтенды | см. Q4 (зависимость и ограничения); для одного модуля выгоды нет |

**Рекомендация:** A. Публичный API — один импорт `desbordante`, дробить нечего; `NB_STATIC` — дефолт nanobind и рекомендован для одного модуля.

**Если спросят «не вырастет ли бинарник?»:** при одном модуле — нет: nanobind встраивается один раз; рост возможен только при появлении второго расширения, тогда и вернёмся к `NB_SHARED`.

### Q6. Суб-интерпретаторы и логирование: отказываемся от per-interpreter изоляции?

**Почему архитектурный:** nanobind **не поддерживает мультиинтерпретаторы/embedding** (в исходниках 3.1.0 нет ни одного упоминания subinterpreter). Сейчас `py_util/logging.cpp` держит реестр логгеров по `py::subinterpreter::current().id()`, то есть предполагает изоляцию логирования по суб-интерпретаторам. Это придётся убрать или заменить.

**Варианты:**

| Вариант | + | − |
|---|---|---|
| **A. Один process-wide logger (рекомендуется)** | простой потокобезопасный sink; полностью совместимо с abi3; меньше кода | теряется изоляция логов между суб-интерпретаторами (если кто-то их использует) |
| **B. Оставить реестр, получая id интерпретатора через CPython API** (`PyInterpreterState_GetID`/`PyThreadState_GetInterpreter`) | сохраняет текущее поведение | эти функции не в limited API → abi3-сборка ломается; противоречит Q2 |
| **C. Оставить pybind11 только ради логирования** | сохраняет суб-интерпретаторы | смешивать pybind11 и nanobind в одном модуле технически можно (`nb::register_module`), но типы между ними не передаются, растёт бинарник и сложность; противоречит цели миграции |

**На что влияет:** `py_util/logging.cpp` (переписывается), `md/object_similarity_measure.h` (комментарий/TODO), release notes.

**Рекомендация:** A. Если владельцы подтверждают, что суб-интерпретаторы никто не использует, вопрос закрывается сразу; если используют — зафиксировать это как известное ограничение релиза.

**Если спросят «а что именно ломается?»:** сейчас sink выбирает логгер по id текущего суб-интерпретатора; после миграции будет один логгер на процесс. Для одноинтерпретаторного запуска поведение идентично.

### Q7. Формат pickle: гарантируем ли обратную совместимость сериализованных объектов?

**Почему архитектурный:** `py::pickle` в nanobind отсутствует — 22 места переписываются вручную на `__getstate__`/`__setstate__`. Если формат состояния (`tuple` из схемы/вертикали/колонки и т. п.) сохранится побайтово-семантически, то pickle, сделанный старой версией desbordante, можно будет загрузить новой (и наоборот, что важнее — старые окружения не увидят разницы).

**Варианты:**

| Вариант | + | − |
|---|---|---|
| **A. Сохранить формат 1:1 (только API-замена)** | пользовательские pickle не ломаются; минимум работы | нужно аккуратно повторить структуру состояний во всех 22 местах |
| **B. Улучшить формат (версионирование состояния)** | чище и надёжнее в будущем | ломает совместимость; нужен migration path |

**На что влияет:** все 16 файлов с `py::pickle` (см. `REPORT.md` §4.4.2), `py_util/table_serialization.*`, Python-тесты (добавить round-trip).

**Рекомендация:** A. Причина: миграция и так масштабная; менять формат сериализации в том же релизе — лишний риск.

**Если спросят «а как убедимся?»:** тест: создать pickle на текущей (pybind11) сборке, загрузить на nanobind-сборке, и наоборот; плюс round-trip для каждого из 16 классов.

### Q8. Публичный API: допустимы ли несовместимые изменения в этом релизе?

**Почему архитектурный:** даже при идеальной механической замене есть наблюдаемые отличия nanobind:

1. `nb::enum_` — настоящий `enum.Enum`/`IntEnum`: `int(member)` больше не работает (нужно `.value`), меняется `repr`/сравнение с числами (затрагивает `gdd.DistanceMetric`, `CmpOp`);
2. `None` не принимается для аргументов, не помеченных `.none()` (потенциально `_set_option(name, None)` — сейчас это «сбросить в default»);
3. исключения: `ConfigurationError` остаётся наследником `ValueError` (сохраняем), но сообщения/типы могут отличаться в краевых случаях (nanobind строже к приведению целочисленных аргументов: требует `__index__`, без усечения float);
4. `__hash__`/`__eq__` остаются, но pickle теперь через новую реализацию.

**Варианты:**

| Вариант | + | − |
|---|---|---|
| **A. Разрешить точечные breaking changes и описать их в release notes** | не тратим силы на эмуляцию; чище API | пользователи, передававшие enum как int или ждавшие `None`-приведение, сломаются |
| **B. Сохранить поведение 1:1 (эмуляция)** | полная совместимость | эмуляция `int(enum)` и None-приведения — костыли, которые придётся вечно поддерживать |

**На что влияет:** `gdd/bind_gdd_verification.cpp` (enum), `bind_main_classes.cpp` (`_set_option`), README/README_PYPI, release notes, тесты.

**Рекомендация:** A, но с явной проверкой: прогнать `test_bindings.py`, `test_data_stats.py` и примеры; в release notes перечислить 3–4 отличия.

**Если спросят «насколько это больно для пользователей?»:** судя по репозиторию, enum'ы используются редко (в тестах/примерах обращений `int(member)` нет), а None-сброс — внутренний служебный вызов `_set_option`; внешний API `load_data`/`execute` принимает именованные аргументы и не требует None.

### Q9. Производительность биндингов: какой регресс допустим?

**Почему архитектурный:** nanobind добавляет ограничения: компилирует биндинги с `-Os`, не включает LTO (в отличие от `pybind11_add_module`, который включал `pybind11::lto`), а abi3 дополнительно замедляет горячие пути. При этом сами алгоритмы desbordante — C++ и от биндингов не зависят, поэтому важен только overhead перехода Python→C++ и конструирования объектов.

**Варианты:**

| Вариант | + | − |
|---|---|---|
| **A. Оставить дефолты nanobind (`-Os`, без LTO)** | меньше бинарник, быстрее сборка | возможен регресс на микрооперациях (создание объектов, частые короткие вызовы) |
| **B. Включить `LTO` / `NOMINSIZE` при регрессе** | возвращает скорость | дольше линковка, больше бинарник; LTO может конфликтовать с sanitizer-сборками |
| **C. Ввести бюджет регресса и мерить `src/tests/benchmark` до/после** | решение на данных, а не на ощущениях | нужны время и стабильное окружение для замеров |

**На что влияет:** `src/python_bindings/CMakeLists.txt` (`nanobind_add_module(... LTO/NOMINSIZE)`), корневой `DESBORDANTE_USE_LTO`, CI-бенчмарки.

**Рекомендация:** C с дефолтом A: сначала собрать дефолтно, прогнать бенчмарки, включать LTO/NOMINSIZE только при подтверждённом регрессе.

**Если спросят «а abi3 сильно медленнее?»:** по замерам nanobind — единицы процентов на микроуровне (пример из changelog: ~75 → ~80 нс/операция), на реальных алгоритмах desbordante (тяжёлый C++ внутри) это в пределах шума; главный риск — не abi3, а потеря LTO.

### Q10. Процесс: big-bang или постепенная миграция, кто следит за новыми Python?

**Почему архитектурный:** nanobind официально поддерживает гибридный режим (`PYBIND11_MODULE` + `nb::register_module`), но типы между pybind11 и nanobind не передаются. Значит, либо один большой PR, либо долгий период, когда часть API на pybind11, часть на nanobind (и каждый обмен типами между ними — ошибка времени выполнения). Плюс после abi3 меняется процесс поддержки новых версий Python: пересборка больше не нужна, но нужен присмотр за пререлизами и abi3audit.

**Варианты:**

| Вариант | + | − |
|---|---|---|
| **A. Big-bang: одна ветка, все 106 файлов, один релиз** | нет гибридного периода с несовместимыми типами; чистая история | большой PR; дольше не зелёный main |
| **B. Поэтапно с гибридным рантаймом** | можно компилировать и тестировать частями | риск обмена типами между `py::`/`nb::`; дольше живут два набора include'ов и флагов; сложнее CI на переходный период |
| **C. Feature-flag сборки (`DESBORDANTE_BINDINGS_STABLE_ABI`)** | можно выпускать обычные колёса и abi3 из одной ветки; удобно для варианта C из Q1 | две конфигурации нужно тестировать постоянно |

**На что влияет:** стратегия ветки/PR, CMake-опции, CI, release notes.

**Рекомендация:** A (с фазовым порядком внутри ветки из `REPORT.md` §8) + отдельная опция сборки только если Q1/Q4 выберут гибрид/split.

**Процесс после abi3 (нужно назначить ответственного):**
* раз в цикл CPython добавлять пререлизную версию в тестовую матрицу (`CIBW_ENABLE: cpython-prerelease`) и убеждаться, что старое abi3-колесо импортируется и тесты проходят;
* следить за выводом `abi3audit --strict` (cibuildwheel запускает автоматически);
* обновлять зависимости/README, если новое окружение (pandas и т. п.) требует изменений;
* не «бампать» сборку ради самого факта выхода новой версии — это и есть выгода.

## 5. Мини-FAQ: ответы на неожиданные встречные вопросы

**«А это точно не сломает совместимость с существующими скриптами?»**
Основной API (`load_data`, `execute`, `get_*`) сохраняется; известны 4 отличия: `int(enum)` → `.value` (только gdd), более строгий `None`, иная реализация pickle (формат сохраняем), сообщения об ошибках. Всё перечисляется в release notes.

**«Почему нельзя остаться на pybind11 и просто включить limited API?»**
В выпущенном pybind11 3.1.0 такой опции нет (есть открытый issue #5905), поддержка живёт в невлитом PR #6198. Опираться на невлитую ветку рискованнее, чем на релизный nanobind, который умеет abi3 с версии 1.3.

**«Разве abi3 не медленный?»**
Замедление есть на микроуровне (nanobind в abi3 не может напрямую читать внутренние структуры), на тяжёлых C++-алгоритмах оно незаметно. Замеры сделаем на `src/tests/benchmark`.

**«Что будет, когда выйдет Python 3.16?»**
Старое abi3-колесо установится и загрузится; нужно только прогнать тесты на пререлизе и убедиться, что окружение (pandas и пр.) совместимо. Пересборка и релиз не обязательны.

**«А на free-threaded старые колёса заработают?»**
Нет. Free-threaded требует либо отдельного колеса под свою версию (`cp313t`), либо `abi3t` (3.15+, только split mode). Если мы отказываемся от FT (Q3), при импорте нашего расширения на no-GIL интерпретаторе Python сам включит GIL и предупредит — это ожидаемое поведение.

**«Кто ещё так делает?»**
cryptography (39 abi3-колёс, включая уже `cp315-abi3.abi3t`), Cython (`cp39-abi3`). Крупные научные пакеты (NumPy, SciPy, pydantic-core) пока без abi3, но это не мешает нам: C-API NumPy мы не используем.

**«Сколько это займёт?»**
Оценки в днях лучше не давать на созвоне. Объём фиксирован: 106 файлов биндингов, 22 pickle-а, 115 `.cast<T>()`, 1 кастомный caster, ~15 специальных файлов, плюс сборочные/CI/доковые правки (полный перечень — `MIGRATION_CHECKLIST.md`). Порядок фаз — `REPORT.md` §8.

**«А можно сделать это после релиза X?»**
Технически да, но: (1) чем дольше, тем больше новых биндингов напишут на pybind11 и тем больше объём миграции; (2) выгода abi3 накапливается с каждым новым Python; (3) один и тот же код нельзя одновременно поддерживать в двух стилях без гибридных ограничений (Q10).

**«Что если владельцы скажут, что free-threaded нужен срочно?»**
Тогда фиксируем: abi3 (linked) откладывается, собираем `FREE_THREADED` per-version колёса, проводим аудит потокобезопасности (`md`, логирование, custom metrics), а abi3t рассматриваем после 3.15t и перехода на split mode. Это не блокирует остальную миграцию — она одинакова.
