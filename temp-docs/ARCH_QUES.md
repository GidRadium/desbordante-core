**Архитектурные вопросы, связанные с миграцией pybind11 -> nanobind.**

1) **Можем ли убрать поддержку Python 3.10/3.11?**
- (V0) Если хотим оставить чисто linked abi3 3.12+ и одно колесо на платформу. (CMake ≥ 3.26 (Development.SABIModule) и заморозка C API на срезе 3.12, возможен регресс производительности, связанный с самим Stable ABI)
- (V1) Альтернатива-1 - per-version колёса 3.10/3.11 + linked abi3 3.12+.
- (V2) Альтернатива-2 - split mode (3.10+). (Основная проблема - рантайм-зависимость от nanobind-backend, если когда-нибудь понадобятся musllinux, PyPy, Emscripten или статически слинкованный C++ runtime — split mode не подойдёт)
- (V3) Альтернатива-3 - отказаться от Stable ABI. (CMake не меняется (3.25+), нет оверхеда limited API, меньше изменений в сборке)

2) **Существуют ли сценарии с суб-интерпретаторами?**
- Да - не сможем перейти на nanobind.
- Нет - надо поправить logging.cpp

3) **Можем ли отказаться от free-threading?**
- Stable ABI не поддерживает. Да - (V0)
- Если хотим сохранить, то только (V2, только 3.15t) или (V3)
